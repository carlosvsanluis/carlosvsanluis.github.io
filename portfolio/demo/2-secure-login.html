Creating customer accounts and secure loginCréation des comptes clients et connexion sécurisée

Customers need an account to see their quotes, claims and documents. There are two ways to build this: A. external users with MFA on a Power Pages portal, or B. a custom web portal with its own login, connected to Dataverse. Either way, each customer sees only their own data.

Le client a besoin d'un compte pour consulter ses devis, sinistres et documents. Deux façons de le construire : A. des utilisateurs externes avec MFA sur un portail Power Pages, ou B. un portail web sur mesure avec sa propre connexion, relié à Dataverse. Dans les deux cas, chaque client ne voit que ses propres données.

Two options for customer accountsDeux options pour les comptes clients

Option A: external users with MFA (Power Pages)Option A : utilisateurs externes avec MFA (Power Pages)

Customers create a Microsoft Entra External ID account with multi-factor authentication and sign in to a Power Pages portal. Power Pages reads Dataverse directly, and its built-in permissions decide what each customer can see.

Le client crée un compte Microsoft Entra External ID avec authentification multifacteur et se connecte à un portail Power Pages. Power Pages lit Dataverse directement, et ses autorisations natives déterminent ce que chaque client voit.

Option B: custom web portal linked to DataverseOption B : portail web sur mesure relié à Dataverse

A web application I host myself (ASP.NET Core on Azure App Service) handles customer sign-up and login. Its server talks to Dataverse through the Web API or Custom APIs, using an application identity whose secrets sit in Key Vault. This is the pattern I already run in production.

Une application web que j'héberge moi-même (ASP.NET Core sur Azure App Service) gère l'inscription et la connexion. Son serveur dialogue avec Dataverse via l'API Web ou des Custom APIs, avec une identité applicative dont les secrets sont dans Key Vault. C'est le modèle que j'exploite déjà en production.

For the demo I build option A first, because it's fastest to show. I then document option B, since it mirrors the API layer I designed in my current job.

Pour la démo, je réalise d'abord l'option A, la plus rapide à montrer. Je documente ensuite l'option B, qui reprend la couche d'API que j'ai conçue dans mon poste actuel.

Option A: build stepsOption A : étapes de réalisation

  1. Create the Power Pages siteI start from a blank template inside the AssurDemo solution, with Home, My space, Quotes and Claims pages.
  2. Set up Entra External IDI create an external tenant and a sign-up / sign-in user flow (email and password, or a one-time code), turn on MFA, and apply the insurer's branding.
  3. Connect it to Power PagesI add External ID as an OpenID Connect provider, switch off local logins and the other providers, and set a session timeout.
  4. Link each account to a contactOn first sign-in, the portal creates or matches a Dataverse contact. That record is what every permission check relies on.
  5. Web roles and table permissionsA role called "Signed-in customer" has Contact-scope permissions. Customers can read their own quotes, claims and files, create new ones, and nothing more.
  1. Créer le site Power PagesJe pars d'un modèle vierge dans la solution AssurDemo, avec les pages Accueil, Mon espace, Devis et Sinistres.
  2. Configurer Entra External IDJe crée un tenant externe et un parcours d'inscription / connexion (e-mail et mot de passe, ou code à usage unique), j'active la MFA et j'applique la charte de l'assureur.
  3. Le relier à Power PagesJ'ajoute External ID comme fournisseur OpenID Connect, je désactive les connexions locales et les autres fournisseurs, et je fixe une durée de session.
  4. Lier chaque compte à un contactÀ la première connexion, le portail crée ou retrouve un contact Dataverse. C'est sur cet enregistrement que reposent tous les contrôles d'accès.
  5. Rôles web et autorisations de tableUn rôle « Client connecté » a des autorisations de portée Contact. Le client peut lire ses propres devis, sinistres et fichiers, en créer de nouveaux, et rien de plus.

Option B: build stepsOption B : étapes de réalisation

  1. Create the web applicationAn ASP.NET Core web app hosted on Azure App Service, HTTPS only, with My space, Quotes and Claims pages.
  2. Add customer loginThe app signs customers in through Entra External ID (OpenID Connect) with MFA, so it never handles passwords itself. A self-managed login is possible, but then it needs strong password hashing (BCrypt) and MFA built in.
  3. Give the server its own identity in DataverseI register an application, create a matching application user in Dataverse, and give it a least-privilege security role that covers only the portal's tables.
  4. Keep secrets out of the codeThe app's Managed Identity reads its credentials from Azure Key Vault. Nothing sensitive sits in configuration files or source control.
  5. Talk to Dataverse server-side onlyThe browser never calls Dataverse directly. The server calls the Dataverse Web API or dedicated Custom APIs, which validate the inputs, and adds the signed-in customer's contact ID as a filter on every query.
  6. Link each account to a contactOn first login, the server finds or creates the Dataverse contact and stores the identity provider's unique user ID on it.
  7. Log and monitorEvery call carries a correlation ID through to Dataverse and is logged in Application Insights, the same observability pattern as my production APIs.
  1. Créer l'application webUne application web ASP.NET Core hébergée sur Azure App Service, en HTTPS uniquement, avec les pages Mon espace, Devis et Sinistres.
  2. Ajouter la connexion clientL'application connecte les clients via Entra External ID (OpenID Connect) avec MFA, sans jamais manipuler elle-même les mots de passe. Une connexion maison est possible, mais elle exige alors un hachage robuste (BCrypt) et une MFA intégrée.
  3. Donner au serveur sa propre identité dans DataverseJ'enregistre une application, je crée l'utilisateur d'application correspondant dans Dataverse, et je lui donne un rôle de sécurité au moindre privilège, limité aux tables du portail.
  4. Garder les secrets hors du codeL'identité managée de l'application lit ses identifiants dans Azure Key Vault. Rien de sensible dans les fichiers de configuration ni dans le dépôt de code.
  5. Interroger Dataverse uniquement côté serveurLe navigateur n'appelle jamais Dataverse directement. Le serveur appelle l'API Web Dataverse ou des Custom APIs dédiées, qui valident les entrées, et ajoute l'identifiant du contact connecté comme filtre à chaque requête.
  6. Lier chaque compte à un contactÀ la première connexion, le serveur retrouve ou crée le contact Dataverse et y enregistre l'identifiant unique fourni par le fournisseur d'identité.
  7. Journaliser et superviserChaque appel transporte un identifiant de corrélation jusqu'à Dataverse et est tracé dans Application Insights, le même modèle d'observabilité que mes API en production.
In option B, the application user can read every customer's data, so a single missing filter in the code would expose other customers. That's why all Dataverse access goes through a small set of server-side functions that always apply the filter, with tests that try to break it.
Dans l'option B, l'utilisateur d'application peut lire les données de tous les clients : un seul filtre oublié dans le code exposerait d'autres clients. C'est pourquoi tout accès à Dataverse passe par un petit nombre de fonctions serveur qui appliquent toujours le filtre, avec des tests qui tentent de le contourner.

Common to both optionsCommun aux deux options

  1. Lock down the back officeAdvisors sign in with the company's Entra ID and get least-privilege security roles: "Advisor" and "Senior advisor" (who can approve). Sensitive columns such as bank details are protected with column security.
  2. Pass the identity to the chatbotI configure authentication in Copilot Studio so that "my policy" questions use the signed-in customer's identity and data.
  3. Try to break itI open another customer's record by changing the ID in the URL (it must fail), call the APIs without a valid session, and check HTTPS, cookie and header settings.
  1. Verrouiller le back-officeLes conseillers se connectent avec l'Entra ID de l'entreprise et ont des rôles au moindre privilège : « Conseiller » et « Conseiller senior » (qui peut valider). Les colonnes sensibles comme les coordonnées bancaires sont protégées par la sécurité de colonne.
  2. Transmettre l'identité au chatbotJe configure l'authentification dans Copilot Studio pour que les questions sur « mon contrat » utilisent l'identité et les données du client connecté.
  3. Essayer de le casserJ'ouvre le dossier d'un autre client en changeant l'identifiant dans l'URL (cela doit échouer), j'appelle les API sans session valide, et je vérifie HTTPS, cookies et en-têtes.

Security and complianceSécurité et conformité

In both options: consent and a privacy notice at sign-up, MFA for every customer, auditing turned on, and no customer passwords stored in Dataverse. That last rule is the lesson from my real-world password migration work.
Dans les deux options : consentement et mention d'information RGPD à l'inscription, MFA pour chaque client, audit activé, et aucun mot de passe client stocké dans Dataverse. Cette dernière règle est la leçon de mon travail réel de migration des mots de passe.
